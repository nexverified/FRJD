# Transaction spine security model — Sprint 1

## Boundaries

- Customer access is a 256-bit random capability secret generated by Web Crypto before submission. The database stores only SHA-256. The private URL uses a fragment; JavaScript sends `Authorization: Bearer` over HTTPS. A public `FRJD-PR-` reference alone returns 401. This is possession-based access, not email/WhatsApp identity; a lost/leaked link requires manual support and a future token-rotation flow.
- The Worker-only operator console requires a strong `FRJD_ADMIN_TOKEN` environment secret, checked on every `/api/operator/*` call. The UI holds it in memory only. No simulated cookie, browser localStorage or customer token grants operator rights. The existing `/api/admin/enquiries` compatibility endpoint remains separate. A shared operator credential is suitable only for a tightly controlled initial single-operator deployment; named accounts, MFA and audit attribution are required before a wider staff rollout.
- The operator page is not included in GitHub Pages output. The Worker uses its CSP/security headers. The Pages site may fetch only the explicit customer API routes via exact-origin CORS; no operator endpoint receives Pages CORS. Server-to-server Origin spoofing is not relied on as authorization.
- All mutating API bodies require JSON and strict field types/lengths. Anonymous request creation has an hourly IP-based rate limit; authenticated operator and customer mutations do not yet have a separate throttle. Database statements use bound parameters. HTML/UI renders untrusted strings with `textContent` or escaped server templates, never `innerHTML` with user content.

## Product URL rules

Normalize once with `URL`: accept only absolute HTTP(S); reject credentials, whitespace/control characters, overlength strings and invalid hostnames. Remove fragments and default ports. Detection is based on parsed hostname (including exact domain/subdomain boundaries), not substring regex over the whole URL. Do not fetch the URL in Sprint 1. If future fetching is introduced, block private/link-local/loopback/localhost and revalidate **every** redirect, enforce time and response-size limits, and use provider-specific adapters rather than an unrestricted proxy. Current no-fetch design makes server-side SSRF in this path impossible.

## Integrity and failure behavior

- D1 `batch()` groups each request creation, review transition, quote publication, or customer action with its event/notification writes. On failure no success acknowledgement is sent. Unique idempotency key + payload hash prevent duplicate requests; expected request version and current quote version prevent stale/changed quote approval.
- Public APIs reveal no contact list, supplier costs, internal notes or other customers' records. Access tokens and operator secrets are never logged or placed in a query string. API responses use no-store; customer page uses `Referrer-Policy: no-referrer` and does not send fragment data as a link to third parties.
- Manual notification rows prove queueing only. Production delivery remains a separate integration with explicit delivery receipts. No email/WhatsApp success is claimed.
- Test cases cover unauthorized access, cross-request visibility, rate limits, unsafe URLs, stale versions, invalid transitions, database failure/rollback, and immutable quote history.
